# LLM Self-Preferencing Bias in Resume Screening: Project Overview and System Architecture

## 1. Project Objective

Automated hiring workflows increasingly deploy large language models (LLMs) for resume screening, while applicants concurrently leverage generative AI to draft and polish application materials. This project evaluates **AI self-preference bias**—the tendency of evaluator LLMs to favor text generated by their own architecture over human-written materials or outputs from rival models.

Extending the pairwise benchmarks established by Xu et al., this study investigates candidate evaluation within realistic job-screening environments by measuring relevance scores and interview shortlist rates against real-world job solicitations. Furthermore, it evaluates whether self-preference introduces systemic socioeconomic bias by analyzing disparate impact across applicant education levels using real-world generative AI adoption benchmarks from the Pew Research Center, and measures the efficacy of prompt-level and ensemble-based debiasing interventions.

---

## 2. Experimental Phases

### Phase 0: Data Collection & Preprocessing
* **Resume Corpus**: Ingest 2,484+ human-written resumes across 24 occupational categories from the LiveCareer dataset.
* **Job Postings**: Ingest scraped job descriptions categorized by Standard Occupational Classification (SOC) codes.
* **Text Extraction & Redaction**: Use PyMuPDF to extract text from resume PDFs, isolate original human executive summaries, and produce redacted candidate profiles containing only objective history, skills, and education.
* **Length Normalization**: Benchmark summary length distributions and enforce a 30–80 word window on all generated summaries to control for length and verbosity bias.
* **Job Matching**: Align resume occupations with corresponding job postings to construct standardized candidate-job evaluation pools.

### Phase 1: Baseline Self-Preference Replication
* **Counterfactual Generation**: Generate AI executive summaries for each candidate profile across multiple frontier and open-weight models (such as GPT-4o, DeepSeek-V3, and LLaMA-3.3-70B).
* **Pairwise Comparisons**: Present pairs of candidate summaries (LLM vs. Human and LLM vs. Rival LLM) to evaluator models without job context, using counterbalanced presentation order (AB/BA) to neutralize position bias.
* **Statistical Parity Measurement**: Calculate the baseline rate at which models select their own generated text over competing options to quantify self-preferencing behavior.

### Phase 2: Real Job-Listing Evaluation & Shortlisting
* **Contextualized Screening**: Evaluate candidate summaries directly against real-world job descriptions.
* **Fit Scoring**: Prompt evaluator models to assign a 1–10 relevance score to each applicant summary relative to the target role.
* **Top-$k$ Shortlisting**: Simulate competitive interview shortlisting by placing 10 candidate submissions (5 human-written, 5 AI-counterfactuals) into candidate pools competing for 4 interview slots.
* **Outcome Measurement**: Measure the empirical difference in selection probabilities between AI-generated and human-authored resumes across occupational domains.

### Phase 3: Education Level & Disparate Impact Evaluation
* **Educational Classification**: Categorize candidate profiles by highest educational attainment, focusing on college graduates versus applicants with a high school education or less.
* **Demographic Weighting**: Model applicant behavior by combining empirical shortlisting rates with Pew Research Center benchmarks indicating that college graduates adopt generative AI at substantially higher rates (~52%) than individuals with a high school education or less (~18%).
* **Fairness Audit**: Compute group-level expected selection rates and determine whether the resulting Adverse Impact Ratio falls below the EEOC Four-Fifths (80%) threshold, assessing whether algorithmic self-preference creates legally actionable disparate impact.

### Phase 4: Bias Mitigation & Remediation
* **System Prompting Guidance**: Re-evaluate candidate pools using modified system instructions directing the evaluator model to disregard generative authorship and focus strictly on candidate qualifications.
* **Majority-Voting Ensembles**: Construct three-model evaluation panels combining frontier evaluators with smaller models that demonstrate lower self-recognition capacity, determining shortlist selections by majority consensus.
* **Efficacy Assessment**: Measure post-mitigation changes in self-preference bias, recompute group selection rates, and evaluate whether interventions successfully restore the Adverse Impact Ratio above the 80% legal standard.

### Component Breakdown
* **`data/`**: Central repository for relational and binary data, containing the primary SQLite database, database connection managers, PDF processing utilities, and local raw storage directories.
* **`docs/`**: Stores formal course deliverables, literature references, and project notes.
* **`pipeline/`**: Houses shared infrastructure configurations, prompt templates, multi-provider API abstractions, and sub-packages dedicated to each experimental phase.
* **`results/`**: Analytical workspace containing exploratory notebooks, generated figures, and LaTeX tables formatted for publication and final reports.
* **`README.MD`**: Provides execution workflows, dependency definitions, and environment setup guidelines.

## 4. System Architecture

The software architecture is structured across four decoupled layers to ensure experimental modularity, fault tolerance, and reproducibility.

### Layer 1: Data & Storage Foundation (`data/`)
The persistence layer centers on `resume_bias.sqlite`, managed by `schema.sql`. Connection management, transactional consistency, and SQLite migrations are encapsulated within `db_core.py`. PDF parsing and visual redactions are handled by `pdf_processor.py`, which reads raw resumes from `data/pdfs/original/` and writes summary-redacted documents to `data/pdfs/redacted/`.

### Layer 2: Shared LLM Engine (`pipeline/` Root)
The engine centralizes model access and prompt structures across all experimental stages:
* **`config.py`**: Manages environment variables, rate limits, model registries, and runtime parameters.
* **`prompts.py`**: Stores version-controlled templates for summary generation, blind pairwise evaluation, job-fit scoring, and debiased system instructions.
* **`base_llm.py`**: Provides a unified API interface across multiple model providers (OpenAI, Anthropic, DeepSeek, Google, and open weights via vLLM), returning a standardized `LLMResult` data structure containing generated text, token usage counts, thinking token metrics, and request latency.

### Layer 3: Phase Performers & Orchestrators (`pipeline/phase0`–`phase4`)
Each phase implements a modular **Triad Pattern** to ensure fault-tolerant, reproducible execution:
* **DB Performer**: Executes parameterized, idempotent SQL queries to extract pending candidate records and atomically commit phase outputs.
* **LLM Performer**: Binds database records to prompt templates, dispatches API requests through `base_llm.py`, and parses model responses (e.g., choice selections, 1–10 fit ratings, ranked shortlists).
* **Phase Orchestrator**: Connects the DB and LLM performers within a checkpoint-based batch execution loop, allowing interrupted runs to resume immediately without duplicate API invocations or redundant compute costs.

### Layer 4: Reporting & Analytics (`results/`)
The analytics layer translates experimental database records into final reporting deliverables. Using `db_core.py`, `analysis.ipynb` loads data into Pandas structures to compute statistical parity gaps, regression models with occupation controls, and Adverse Impact Ratios. Camera-ready figures and publication-formatted LaTeX tables are exported directly to `results/figures/` and `results/tables/`.
